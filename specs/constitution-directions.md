# 憲法內容方向討論稿

## 文件目的

本文件只用來界定專案憲法應該討論與涵蓋的方向，不是正式憲法，也不直接產生實作規則。

正式憲法仍以 `.specify/memory/constitution.md` 為準。

## Project Mission and Domain Boundary

### 專案核心使命

為哥倫布 Agent 提供針對單一指定法規資料庫網站的 MCP 爬蟲 API。MCP 依 Agent 指定的法規種類與月份，在該網站搜尋資料，並依既定規格忠實呈現來源原文，讓 Agent 後續的法規分類能建立在正確資料上。

### 主要使用者與價值

主要使用者是環安衛部門所使用的哥倫布 Agent。Agent 可能透過 system prompt 定義法規分類規則，再呼叫本專案提供的 MCP。系統的價值是按照指定網站與查詢期間取得資料，降低人工查找成本，並確保後續分類使用的是與來源原文一致的內容。

### 系統責任邊界

系統負責針對一個指定法規資料庫網站，依請求搜尋指定月份與指定種類的資料，取得網站內容，依 `spec` 定義的格式呈現，並回報來源與查詢範圍等必要資訊。

目前規劃為一隻 MCP 對應一個網站。當 Agent 指定搜尋 9 月資料時，系統應依該網站的查詢規則搜尋 `09/01` 至 `10/01` 前一天的資料。

系統不負責法規分類、分類規則執行、翻寫、摘要、解釋、法規效力判定或法律意見。

### 非目標

- 不提供法律意見、個案法律結論或法律責任判定。
- 不負責法規分類或替哥倫布 Agent 執行分類規則。
- 不得翻寫、摘要、推論、補全或改變網站原文的語意；資料必須與原文一致，並依 `spec` 的格式呈現。
- 連線失敗、格式異常、資料不完整或無法確認時，必須明確回報異常，不得猜想、補造或以推測取代來源資料。
- 不為尚未確認的需求預先建立不必要的功能、抽象或整合。

### 階段一決策紀錄：專案使命與責任邊界

狀態：已確認，仍保留待確認的技術細節。

已確認事項：

- 本專案提供給哥倫布 Agent 使用的 MCP，而不是法規分類系統。
- MCP 只負責對應網站的搜尋與資料擷取；目前規劃是一隻 MCP 對應一個網站。
- Agent 可以指定法規資料種類與月份；例如指定 9 月時，搜尋期間為 `09/01` 至 `10/01` 前一天。
- 爬回來的資料必須與網站原文一致，不得翻寫、摘要、推論或自行補全。
- 回應必須依功能 `spec` 所定義的格式呈現，不由 MCP 自行增加語意轉換。
- 連線失敗或格式異常時必須回報異常，不得猜想或產生替代資料。
- 法規分類與分類規則由哥倫布 Agent 負責，不屬於本 MCP 的責任。

待確認事項：

- 「指定種類」在各網站上的具體查詢參數與允許值，應由各網站的功能 `spec` 定義。
- 月份區間是否一律採來源網站時區，以及 `10/01` 當日資料是否明確排除，應在功能 `spec` 中固定。
- 「與原文一模一樣」是否包含 HTML 標籤、空白、換行、編碼與頁面順序，應在資料擷取與呈現規格中定義可驗證的保留範圍。
- 發生部分資料成功、部分資料異常時，是整次回報失敗，還是分筆標示異常，需在功能 `spec` 中決定。

## 憲法的定位

憲法應描述整個專案長期適用、跨功能、不可任意違反的原則與治理要求。

### 原有方向一：資料正確性與完整性

狀態：已確認納入憲法主幹。

主幹原則：

1. 回傳資料必須忠實反映來源網站原文，不得自行修改、摘要或推論。
2. 在符合查詢條件的範圍內，不得任意漏掉應回傳的資料；若無法確認資料完整性，不得將結果當作查詢成功。
3. 遇到網路問題、無法取得資料或其他不確定情況時，必須明確回報異常，不得猜測或以推測內容取代資料。

下游 `spec` 可以定義各網站的查詢條件、完整性判定與驗證方式，但不得降低或違反上述主幹原則。

### 原有方向二：資料可溯源與資料治理

狀態：已確認納入憲法主幹。

主幹原則：

1. 查詢結果必須說明資料來自哪一個法規網站。
2. 查詢結果必須提供本次搜尋取得的資料總數，使接收資料的 Agent 能確認結果範圍。
3. 每一筆法規資料都必須具備可追溯至來源的 `ref`。

各網站的 `spec` 或契約可以定義 `ref` 的具體格式、唯一性與其他來源資訊，但不得省略來源網站、資料總數或逐筆追溯能力。

### 原有方向三：外部來源與爬取合規

狀態：已確認納入憲法主幹。

主幹原則：

1. 使用外部法規網站前，必須確認並遵守適用的來源規範，包括 `robots.txt`、網站使用條款、官方 API 或其他存取政策。
2. 資料擷取必須遵守來源要求的存取方式、頻率限制與其他合理的使用限制，不得以技術方式規避禁止或限制。
3. 來源規範不明、互相衝突或無法確認是否允許存取時，不得自行猜測為允許；應回報異常或交由適當的人員確認。

各網站的 `spec` 可以定義來源規範的檢查方式、允許的查詢行為與頻率設定，但不得降低上述合規要求。

### 原有方向四：API 契約與相容性

狀態：已確認納入憲法主幹。

主幹原則：

1. 每一隻 MCP API 都必須提供並遵守經批准且可驗證的 API 介面契約。
2. MCP 至少接受搜尋網站與搜尋月份作為查詢條件。
3. MCP 回傳的法規資料至少必須包含日期、種類、標題與原文超連結。
4. API 契約、實作、文件與測試必須保持一致；介面變更不得在未審查或未說明影響的情況下破壞既有 Agent。
5. OpenAPI 3.0、Swagger 文件與 Azure MCP 的具體規範，應由獨立的 API governance 分支文件承接。

附圖所示的網站畫面與 HTML 片段屬於來源資料呈現範例，不直接作為憲法中的 API schema；實際欄位與契約應在下游文件定義。

API governance 分支應另行定義：

- OpenAPI 3.0 文件結構與必要欄位。
- Swagger 文件或 Swagger UI 的產出與驗證方式。
- MCP 輸入、輸出、錯誤與相容性規範。
- Azure MCP 所要求的介面格式、限制與遷移檢查。

憲法只要求所有 MCP API 遵守經批准、可驗證且與實作一致的 API 契約，不直接承擔上述分支的技術細節。

本專案目前以 Python `3.12.2` 作為開發基準，並由專案根目錄的 `.python-version` 指定。正式的最低支援版本、依賴版本與可重現環境設定，應在技術標準分支與專案設定檔中明確鎖定。

### API 架構與共用資料模型決策

狀態：已確認作為 API 技術規範候選，OpenAPI 與 Azure MCP 細節留在 API governance 分支，具體實作留在各功能 `plan`。

本專案採用輕量分層架構，概念上接近 MVC，但不建立目前不需要的 View 與資料庫 Repository：

- **Presentation layer**：由 Controller 接收 MCP/API 請求、驗證輸入、呼叫應用服務，並依 OpenAPI 契約回傳成功或失敗結果。
- **Business/Application layer**：由 Service 控制查詢流程；網站專用 crawler/parser 負責取得與解析指定網站資料。這一層不得負責法規分類、摘要或法律判斷。
- **Persistence layer**：目前沒有資料保存需求，因此暫不建立資料庫或 Repository。執行紀錄可透過 logging 記錄，但 logging 屬於共用基礎設施，不代表已建立 Persistence layer。
- **Infrastructure**：提供 HTTP client、logging、設定與其他外部技術依賴，並與業務規則保持分離。

所有網站 API 優先使用共用輸出模型呈現日期、來源網站、分類、標題、法規連結與 `ref`；網站特有資料放入 `metadata`，由網站專用 parser 解析後提供，不得取代共用欄位。

### 技術選型邊界

為避免 SDD 在規劃與實作階段偏離目前決策，初期 API 與爬蟲實作固定採用以下套件：

- **Python `3.12.2`**：目前開發基準，由 `.python-version` 指定。
- **FastAPI**：非同步 API、Controller、OpenAPI 3.0 與 Swagger UI。
- **Pydantic**：請求與回應模型驗證。
- **httpx**：非同步 HTTP 連線與 timeout 控制。
- **selectolax**：HTML 解析與資料擷取。
- **pytest**：parser、資料正確性與 API 契約測試。

依賴套件集中記錄於根目錄的 `requirements.txt`，目前採用相容版本範圍；執行與部署環境必須使用專案虛擬環境安裝依賴。初期不引入 Scrapy、資料庫、Repository 或其他未經需求確認的框架與基礎設施。若後續需要替換套件，必須在 `plan` 中說明原因、影響與相容性驗證，不得由實作自行改變技術邊界。

憲法層級只要求 Python 執行環境、依賴與虛擬環境可被明確追蹤且可重現；具體 Python 版本、套件版本範圍與安裝指令由 `.python-version`、`requirements.txt` 與專案文件承接。

### 原有方向五：安全與資料保護

狀態：已確認納入憲法主幹。

主幹原則：

1. MCP 的輸入參數必須逐項驗證；法規網站只能從專案明確支援的網站清單中選擇，不得由輸入任意指定未支援或未核准的網站。
2. 查詢範圍以月份為基本單位；月份的格式、種類與各支援網站的允許查詢條件，由各網站 `spec` 定義。
3. 每一個 request 都必須記錄必要的輸入參數、實際呼叫的 API 或來源端點、搜尋月份、處理結果與資料筆數，以便日後查核。
4. 執行過程必須留下足以追蹤處理狀態的 log；成功結果應記錄回應狀態與總筆數，失敗結果應記錄可辨識的異常原因。
5. Log 不得洩漏秘密或不必要的敏感資料；未來若加入 token 或其他認證資訊，必須採取適當的遮罩與存取控制。
6. 目前不建立資料庫；但紀錄設計不得阻礙未來將 log 或查詢紀錄導入持久化儲存。

各網站 `spec` 可以定義支援網站清單、輸入欄位、月份格式、API 端點、log 欄位與異常分類，但不得省略 request 驗證、執行追蹤與失敗原因。

### 原有方向七：測試與驗證

狀態：待完成主幹決策；本次討論先確認其文件對應，不將它歸入 API 契約方向。

方向定位：測試與驗證是跨 API、crawler/parser、資料模型與功能規格的品質治理要求。它要驗證的是資料是否正確、完整、可追溯，以及實作是否符合契約；API contract 只是其中一種被驗證的對象。

憲法主幹候選原則：

> 新增或修改的行為必須有相應驗證；法規資料只有在正確性、完整性、來源參照與契約一致性都可被驗證時，才能視為成功。驗證失敗或尚未執行時，必須如實記錄，不得宣稱成功。

文件對應：

- 憲法主幹：保留測試與驗證的長期品質要求。
- 跨領域驗證分支：承接總筆數、分頁完整性、逐筆 `ref` 反查、原文一致性與失敗判定。
- API governance 分支：只承接 API 契約、OpenAPI、Swagger 與 API 相容性驗證。
- 各功能 `spec.md`：定義該網站的查詢條件、來源欄位與可驗證的功能驗收條件。
- `plan.md` 與 `tasks.md`：定義測試實作、執行順序與驗證紀錄。

因此，憲法討論時應以「原有方向七：測試與驗證」作為回溯入口；API 文件中的驗證規則只能視為其中一部分，不得取代方向七的完整治理範圍。

已確認的實作方向：

1. API 採非同步處理，以支援外部網站連線與未來 MCP 整合。
2. 先以資料正確性驗證為主，不為了非同步而犧牲原文忠實性與完整性。
3. 共用輸出欄位確定包含 `date`、`sourceWebsite`、`category`、`title`、`lawUrl` 與 `ref`。
4. 查詢失敗、來源異常或資料不確定時，必須明確回報失敗，不得猜測、補造或把部分結果偽裝成成功結果。

### 原有方向八：效能、可靠性與可擴展性

狀態：已確認納入憲法主幹；具體規範移至 `docs/quality/performance-reliability.md`。

主幹原則：外部網站存取與資料處理必須具備適當的可靠性、資源控制與失敗可追蹤性，不得因重試、非同步或擴充需求而違反來源規範或掩蓋資料異常。

分支承接：timeout、retry、非同步處理、來源頻率、backoff、未來 Job 或資料庫擴充等可執行細節，統一記錄於 `docs/quality/performance-reliability.md`；各網站 `spec` 與 `plan` 只能具體化，不得降低憲法主幹要求。

### 原有方向十：程式設計慣例與可維護性

狀態：已確認納入憲法主幹；具體工具與規則移至 `docs/quality/python-code-quality.md`。

主幹原則：程式碼應遵守一致且可檢查的命名、格式與分層慣例，保持清楚責任、單一主要目的與可維護性；品質檢查未通過或未執行時，不得宣稱變更完成。

分支承接：Python 命名規則、Ruff、Ruff format、Pyright、pytest、分層依賴與維護性檢查，統一記錄於 `docs/quality/python-code-quality.md`。API 對外欄位仍由 API governance 分支規範，不因 Python 內部命名慣例而任意改寫契約。

### 原有方向九：可觀測性與錯誤處理

狀態：已確認納入憲法主幹；具體 log 欄位與錯誤格式由相關分支與功能 `spec` 承接。

主幹原則：系統必須能追蹤每次 MCP request 的處理狀態、成功結果與失敗原因；錯誤資訊應足以支援查核與除錯，但不得洩漏秘密或不必要的敏感資料。未驗證、失敗或不完整的結果不得以正常成功狀態提供。

分支承接：request log、資料驗證紀錄、timeout/retry 紀錄與 API error response 分別由品質驗證、效能可靠性與 API governance 分支具體定義。

### 原有方向十一：使用者體驗與可及性

狀態：確認本專案不直接提供使用者介面；由哥倫布 Agent 承接使用者互動。

主幹原則：本專案作為哥倫布 Agent 使用的 MCP 工具，重點是提供可理解、可驗證且符合契約的 API response。API 必須符合 OpenAPI 3.0 及 API governance 分支規範，並以可轉換至 Azure MCP 為設計目標；不在本專案建立獨立 UI 或 UI 可及性規範。

### 原有方向十二：開發流程、品質門檻與治理

狀態：已確認納入憲法主幹，並遵循 Spec Kit 工作流程。

主幹原則：需求、規格、技術方案、任務、實作與驗證必須依 Spec Kit 的文件分層與流程執行；每項工作都必須能回溯至憲法原則、功能 `spec`、技術 `plan` 或明確的治理分支。品質檢查未執行、失敗或被豁免時，必須如實記錄。

工作回報要求：每次執行 task 時，必須提供本次 task 的執行摘要，並計算及回報 task 數量，至少包含已完成、進行中、未完成或失敗的數量。Task 的狀態必須與 `tasks.md` 保持一致。

分支承接：Spec Kit 的具體命令、`spec.md`、`plan.md`、`tasks.md`、checklist 與驗證流程依專案既有 Spec Kit 規範執行；不在憲法中重複工具操作細節。

## 憲法討論計畫

本次工作先完成憲法草案與決策紀錄，再決定是否更新正式憲法。討論期間，所有新增、修改、取捨與未決事項都只能記錄在本文件，不得直接修改 `.specify/memory/constitution.md`。

### 討論階段

#### 階段一：確認專案使命與責任邊界

確認專案核心使命、主要使用者與價值、系統責任邊界，以及明確的非目標。這一階段的結果決定後續原則是否符合專案真正要解決的問題。

#### 階段二：逐項討論原有 12 個方向

依序檢視原有方向，對每一項記錄：

- 規則要解決的風險或問題。
- 是否適用於全專案。
- 是否屬於長期且不可任意違反的要求。
- 應留在憲法主幹，還是下放到分支文件。
- 若下放，目標文件與承接關係。
- 可接受的例外與核准方式。
- 可執行的驗證方式。

#### 階段三：整理成五大核心原則

將 12 個方向的討論結果歸入以下五個主幹：

1. 技術與架構標準。
2. 安全與資料保護。
3. 效能、可靠性與可觀測性。
4. 程式品質與測試。
5. 資料治理與合規。

這個階段只整理原則與決策，不急著撰寫正式憲法文字。

#### 階段四：建立主幹與分支對照表

為每項已確認規則標記其最終位置：

- 憲法主幹。
- 專門治理文件，例如 API governance、資料治理或資安規範。
- 功能 `spec.md`。
- 技術 `plan.md`。
- OpenAPI contract 或其他契約文件。
- 不納入，或保留為未決事項。

若內容需要從憲法切出，必須先說明切分範圍、理由、目標文件、引用關係與驗證影響，取得討論共識後才能執行切分。

#### 階段五：形成憲法草案

依確認結果整理出正式憲法的候選版本，預計包含：

- Project Mission and Domain Boundary。
- Core Principles 五大核心原則。
- Development Workflow and Quality Gates。
- Governance。

- 五大原則與專案使命一致。

- 憲法沒有混入單一功能、短期技術或具體 API 細節。
- 所有下游分支都有清楚的承接關係。
- 開發流程、品質門檻、例外與修訂治理可被執行。

### 主幹與分支

本專案採用「憲法是主幹、專門規範是分支」的文件治理概念：

- `constitution.md` 是主幹，定義專案使命、責任邊界、長期原則與治理底線。
- API governance、資料治理、資安規範等專門文件是分支，將主幹原則轉化為特定領域可執行、可驗證的規則。
- feature `spec.md`、`plan.md`、`tasks.md` 與 contracts 是更下游的分支，分別描述需求、方案、工作與具體契約。
- 下游文件不得違反主幹；若下游規範與憲法衝突，必須先處理憲法或提出正式例外，不得由實作自行解釋。

這種分層可以避免憲法因單一技術、單一 API 或單一功能的細節而膨脹，也讓專門規範能在不改變專案核心原則的情況下獨立演進。

### 內容切分原則

當討論中的憲法條文開始過於細緻時，應先提出切分提醒，再進行文件拆分。提醒至少應說明：

- 哪一段內容已經從長期原則變成領域規則或實作細節。
- 建議移至哪一份分支文件，以及該文件與憲法的關係。
- 憲法應保留的上位原則與下游文件應承接的具體規則。
- 拆分後需要更新哪些引用、驗證或治理流程。

切分順序應是先確認主幹原則，再建立或更新分支文件，最後才移除憲法中的重複細節。不得在尚未說明切分理由前直接刪除正式憲法內容。

每個方向都應符合以下條件：

- 適用於多個功能，而不是單一功能的細節。
- 預期能長期維持，而不是短期技術選擇。
- 可以被檢查、驗證或在審查時判斷是否符合。
- 違反時會造成重要的品質、風險、合規或維護問題。
- 能明確影響 specification、plan、tasks、實作與驗證。

憲法不應只是團隊偏好、工具清單或技術計畫的摘要。

## 應涵蓋的五大原則

以下五項是正式憲法預計保留的主幹。原本的 12 個討論方向不再作為憲法的平行章節，而是整理為各原則底下的候選規則。

### 一、技術與架構標準

確保系統以清楚、可維護、可演進的技術與架構方式建置。憲法只定義長期標準；具體框架、套件版本與實作方案應下放至 plan 或專門技術規範。

候選規則：

1. 程式碼版本與變更必須可追蹤，重要變更應透過審查與明確的版本控制流程管理。
2. 技術框架、依賴與平台選擇必須符合專案責任邊界，並考量維護成本、安全性與長期支援。
3. 服務、模組與資料責任必須有清楚邊界，不得為尚未確認的需求建立不必要的複雜抽象。
4. 對外 API 必須遵守經批准且可驗證的契約；具體 OpenAPI contract 與 API style rules 應由下游文件承接。
5. API 文件、實作與測試必須保持一致；破壞性變更必須經過明確審查並提供相容性或遷移方案。

### 二、安全與資料保護

確保系統、使用者資料與外部連線受到適當保護，並避免未授權存取、資訊洩漏或不當處理。

候選規則：

1. 所有外部輸入都必須經過驗證、限制與適當的錯誤處理。
2. 認證、授權、秘密、token、連線資訊與個資必須有明確的處理邊界。
3. API 回應、錯誤訊息與 log 不得洩漏不必要的敏感資訊，log 必須具備遮罩與保存政策。
4. 網路連線、TLS、外部服務存取、timeout 與依賴漏洞處理必須符合專案安全要求。
5. 若資料可溯源紀錄包含敏感資訊，必須同時符合最小揭露、存取控制與保存期限要求。

### 三、效能、可靠性與可觀測性

確保系統在正常與異常情況下都能穩定運作，並讓維護者能理解系統與資料處理的狀態。

候選規則：

1. 長時間或不可預期完成的工作不得阻塞一般 HTTP request，應使用可追蹤的非同步 Job Pattern。
2. timeout、retry、backoff、rate limit、idempotency 與 graceful degradation 必須依工作風險設計。
3. Job、爬取、外部來源與資料品質失敗必須能被追蹤，且錯誤結果不得只存在於單一 request 或程序記憶體中。
4. 系統應具備符合需求的結構化 log、metrics、tracing 或其他可驗證的觀測方式。
5. 延遲、吞吐量、資料量與可用性目標應由功能規格或技術計畫定義，不在憲法中固定短期數值。

### 四、程式品質與測試

確保變更可理解、可驗證、可維護，且完成工作的判斷不只依賴程式碼能夠執行。

候選規則：

1. 新增或修改的行為必須有相應的測試或明確記錄不適合自動化測試的理由。
2. 應依風險採用單元、整合、契約、端對端與資料品質測試。
3. API schema、實際輸入輸出、Swagger UI 與契約文件必須保持一致並可驗證。
4. 修復問題時應先建立可重現案例；未執行或失敗的驗證必須如實記錄。
5. 程式碼、文件與使用者可見行為的變更應保持同步，並遵守格式化、lint、型別檢查與 code review 要求。

### 五、資料治理與合規

確保資料從取得、處理、保存到對外提供的過程都可說明、可追溯，並符合來源規範與適用的法律、政策要求。

候選規則：

1. 資料擷取、轉換、整理與輸出必須忠實保留來源意義，不得捏造、遺漏、誤解或扭曲資料。
2. 對外提供的資料必須能追溯至來源、取得時間、版本與適用的處理紀錄。
3. 原始資料、整理資料與摘要資料應能區分，並依需求定義保存、刪除、稽核與存取政策。
4. 啟用外部來源前必須檢查 `robots.txt`、使用條款與合理頻率限制；來源規範不明時不得由實作自行猜測。
5. 無法驗證、格式異常、來源衝突或規範不明的資料，必須依既定政策標示、隔離、停止提供或交由人工確認。
6. 個資、敏感資料與機密資料的處理必須符合適用法規、來源限制與專案資料政策。

## Development Workflow and Quality Gates

憲法原則必須在需求、設計、實作與驗證的各階段被檢查，而不是只在文件完成時宣告符合。

候選規則：

1. `spec.md` 必須說明功能目的、範圍、資料正確性與可追溯性的驗收條件。
2. `plan.md` 必須說明如何落實相關憲法原則，以及必要的技術選擇、風險與驗證方式。
3. `contracts/` 或其他專門規範必須承接憲法與功能規格，並提供可機器或人工檢查的契約。
4. `tasks.md` 必須包含必要的實作、測試、文件同步與品質檢查工作。
5. 合併或發布前，必須完成適用的資料品質、資安、契約、測試與可觀測性驗證。
6. 未執行、失敗或被豁免的品質檢查，必須記錄原因、影響與後續處理方式。

## 不宜直接寫入憲法的內容

以下內容通常應放到其他文件，除非它們是專案長期且不可變的硬性約束：

- 單一功能的需求、欄位與使用情境：放在 `spec.md`。
- 某個功能的具體技術方案、套件版本與資料表設計：放在 `plan.md`。
- 可執行的工作分解與順序：放在 `tasks.md`。
- 單一 API 的完整 request、response 與錯誤案例：放在 API contract 或 OpenAPI 文件。
- 短期效能數字、單一頁面的 UI 細節與一次性部署設定：放在功能規格或技術計畫。
- 尚未經團隊同意的偏好、推測或未驗證的標準。

## 建議的文件分層

```text
.specify/memory/constitution.md
	專案主幹：使命、責任邊界、核心原則與治理底線

docs/api/api-governance.md
	API 分支：全專案 API 風格、相容性與驗證規則

docs/quality/data-validation.md
	跨領域品質分支：爬蟲資料完整性、逐筆來源驗證、原文一致性與失敗判定

docs/quality/performance-reliability.md
	跨領域品質分支：timeout、retry、非同步處理、來源頻率與未來擴充規範

docs/quality/python-code-quality.md
	Python 品質分支：命名、格式、lint、型別檢查、測試與可維護性規範

specs/<feature>/spec.md
	功能分支：使用者需求、範圍與驗收條件

specs/<feature>/plan.md
	技術分支：架構、技術選擇、資料模型與實作方案

specs/<feature>/contracts/openapi.yaml
	契約末節：該功能實際提供的 endpoint、schema、參數與回應

specs/<feature>/tasks.md
	執行分支：依賴順序、實作工作與驗證任務
```

文件之間的關係不是每一份文件都複製上一層內容，而是由上游提供約束、下游提供具體化：

```text
constitution.md
				|
				+-- api-governance.md
				|       +-- feature contracts/openapi.yaml
				|
				+-- feature spec.md
								+-- plan.md
												+-- tasks.md
```

每個下游文件都應能指出自己承接的上游原則；每個具體規則也應能回溯至需求、契約、治理要求或明確的技術決策。

## Governance

憲法是專案文件治理的主幹，優先於個別功能規格、技術計畫、契約與實作。下游文件若與憲法衝突，必須先提出衝突內容與影響，不得由實作自行忽略或解釋。

專門規範與功能文件可以在不改變憲法原則的前提下獨立演進；若某項分支規則已成為跨功能、長期且不可任意違反的約束，才應評估是否回收至憲法主幹。

憲法或其分支規範的修訂，應記錄：

- 變更內容與原因。
- 受影響的文件、契約、實作與驗證。
- 是否涉及不相容變更或遷移工作。
- 審查者、核准者與例外期限。

憲法修訂採語意化版本管理：移除或重新定義原則為 MAJOR，新增或實質擴充要求為 MINOR，不改變規則意義的澄清或文字修正為 PATCH。
