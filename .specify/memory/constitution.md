# 環安小幫手專案憲章

## Core Principles

### 一、資料正確性

資料擷取、整理、轉換與輸出必須忠實保留來源的意義，不得捏造資料或扭曲原意。
資料正確性必須有可檢查的驗證依據；符合 API 契約不等同於資料內容正確。
個別功能規格必須定義適用的正確性驗收條件，技術計畫必須提出驗證方式。

理由：系統提供的資料必須具有可信的依據，避免格式正確但內容錯誤。

### 二、資料可溯源

對外提供的資料必須能追溯至來源與取得時間。
經過轉換、整理或摘要的內容，必須保留足以追查來源及處理過程的紀錄。
溯源方式必須能被驗證，具體儲存結構與技術方案由後續計畫決定。

理由：資料出現疑義時，必須能查明其來源與形成過程。

### 三、爬取規範

爬蟲必須遵守目標網站的 robots.txt、使用條款與合理頻率限制。
啟用來源爬取前，必須檢查上述規範，並保留檢查依據與採用的頻率限制紀錄。
不得只因技術上可以存取，就省略規範檢查。
各來源的具體頻率與控制方式由後續規格及計畫定義，但不得違反本原則。

理由：來源取得方式與資料品質同樣是本專案的基本要求。

### 四、OpenAPI 契約優先

所有對外 HTTP API 必須符合專案的 OpenAPI 規格，並能正確顯示於 Swagger UI。
API 實作、OpenAPI 文件與測試必須保持一致。
任何 API 行為或資料結構的修改，都必須同步更新 OpenAPI 契約。

### 五、Operation ID 命名規則

每一個 API operation 必須具有唯一的 `operationId`，並符合下列規則：

- 使用 lowerCamelCase。
- 採用「動詞＋名詞或名詞片語」結構。
- 清楚表達 API 的實際用途。
- 不得使用模糊名稱，例如 `processData`、`handleRequest`。

正確範例：`queryRegulations`、`retrieveLaw`、`createCrawlJob`、`retrieveCrawlJob`。

### 六、API Description 規則

每一個 API operation 都必須提供清楚的 `description`。
移除空白、Tab、換行等 whitespace 後，字元總數不得超過 1,000 個字元。
Description 應說明 API 的用途、主要輸入條件、成功時的結果，以及重要限制或可能的失敗情況。
這些說明用於讓契約使用者理解操作；若某項不適用，審查時必須說明原因。

### 七、Schema 與 `$ref` 規則

所有 request body、response body 與巢狀物件的 object schema，
都必須定義於 `components/schemas`，並透過 `$ref` 引用。
禁止直接在 operation、request、response 或其他 schema 中定義 inline object schema。
字串、數字、布林值等單純型別參數可以直接定義，不強制建立 `$ref`。

### 八、巢狀結構限制

解析全部 `$ref` 後，物件巢狀深度不得超過三層，此限制為硬性上限。

- 最外層 request 或 response object 為第一層。
- 其直接包含的 object 為第二層。
- 第二層所包含的 object 為第三層。
- 禁止出現第四層 object。

若資料天然超過三層，必須重新設計為扁平結構、識別碼引用，或拆分成不同 API。

### 九、長時間操作

爬蟲、批次處理或其他無法在一般 HTTP request 時限內穩定完成的工作，不得阻塞 HTTP request。
此類操作必須採用非同步 Job Pattern：

- 建立工作時立即回傳 `202 Accepted`。
- Response 必須包含可追蹤的 `jobId`。
- 必須提供查詢工作狀態的 API。
- 工作狀態至少應能區分等待、執行中、完成與失敗。
- 工作結果與錯誤不得只保存在單一 HTTP request 或程序記憶體中。

## 開發流程與驗證要求

後續產生的 specification、plan、tasks、OpenAPI 文件與程式碼，
都必須檢查是否符合本憲章，並記錄符合情形、缺口與驗證依據。

功能完成前必須驗證：

- 資料符合該功能定義的正確性驗收條件。
- 對外提供的資料可追溯至來源、取得時間及適用的處理紀錄。
- 涉及爬取時，已檢查目標網站規範，且實際爬取符合採用的限制。
- OpenAPI 文件可以成功解析。
- Swagger UI 可以正常顯示所有 API。
- 每個 operation 都有唯一且符合規則的 `operationId`。
- 每個 operation 都有符合長度限制的 `description`。
- 不存在違反本憲章的 inline object schema。
- 物件巢狀深度不超過三層。
- API 實際輸入輸出符合 OpenAPI 契約。
- 涉及長時間操作時，符合非同步 Job Pattern 及結果、錯誤保存要求。

尚未執行或無法完成的驗證必須如實記錄，不得宣告為已通過。
