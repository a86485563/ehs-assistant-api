# Crawler Data Validation

## 文件定位

本文件是 API governance 的資料驗證專門分支，定義法規網站爬蟲結果何時可以被視為成功。單一網站的查詢參數、頁面結構與特殊例外由該網站的 `spec.md` 承接，但不得降低本文件的驗證底線。

## 驗證層級

### 1. 查詢條件

確認 request 已通過驗證：

- 網站在支援網站清單中。
- 月份格式正確，且查詢範圍符合該網站 `spec.md`。
- 種類與其他條件符合該網站允許的值。

### 2. 結果總數與完整性

若來源網站提供可靠的總筆數，應記錄為 `sourceTotal`，並確認：

```text
sourceTotal == 實際成功取得並通過驗證的資料筆數
```

同時必須確認：

- 所有符合條件的分頁或結果區段都已處理。
- 沒有未說明的重複資料。
- 沒有因網路、解析或分頁錯誤而跳過資料。
- 每筆資料都符合查詢月份與其他條件。

若來源沒有可靠總筆數，必須依該網站 `spec.md` 定義其他可驗證的完整性判定方式；沒有可靠判定方式時，不得宣稱完整成功。

### 3. 逐筆來源參照

每筆資料都必須：

- 具有 `ref`。
- `ref` 可回到同一個支援網站的來源資料。
- `ref` 不得是無法驗證或自行猜測的連結。
- `ref` 與資料的日期、種類、標題及法規連結能互相對應。

### 4. 原文一致性

回查每筆 `ref` 後，必須確認必要欄位與來源一致：

- 日期。
- 種類。
- `title` 原文。
- `lawUrl`。
- 該網站 `spec.md` 要求保留的其他原始資料。

不得翻寫、摘要、推論、補全或以相似文字取代原文。HTML 標籤、空白、換行與編碼的保留規則，由各網站 `spec.md` 定義並且必須可驗證。

### 5. API 契約

最終 response 必須符合 OpenAPI contract。資料筆數、逐筆項目、錯誤狀態與必要欄位都必須一致。

## 成功條件

只有以下條件全部成立，才能回傳完整成功：

```text
查詢條件正確
AND 完整性可確認
AND 所有結果區段已處理
AND 回傳筆數符合來源總數或既定完整性判定
AND 每筆 ref 有效且可回溯
AND 每筆必要內容與來源一致
AND response 符合 OpenAPI contract
```

## 失敗條件

遇到以下任一情況，必須明確回報失敗或異常，不得猜測、補造或把部分結果偽裝成成功：

- 網路連線失敗或來源無法取得。
- 頁面格式異常或解析結果不完整。
- 總筆數不一致。
- 分頁或結果區段無法確認完整。
- `ref` 不存在、無效或無法回查。
- `ref` 與日期、種類、標題或連結對不上。
- 原文內容無法確認一致。
- 查詢條件不符合來源規範。

失敗 response 必須依 OpenAPI contract 回傳可辨識的錯誤類型與原因。未驗證完成的資料不得以正常成功結果提供。

## 驗證紀錄

每次 request 的 log 至少記錄：

- request 識別資訊與已驗證的輸入參數。
- 支援網站與實際呼叫的來源端點。
- 搜尋月份與查詢範圍。
- `sourceTotal`、實際處理筆數與回傳筆數。
- 驗證結果與 response 狀態。
- 失敗時的驗證階段、異常類型與原因。

Log 不得包含秘密或不必要的敏感資料。未來導入資料庫時，這些紀錄應可轉為持久化資料。
