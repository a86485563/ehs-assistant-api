# Performance, Reliability and Scalability

## 文件定位

本文件是憲法「效能、可靠性與可擴展性」方向的專門分支，承接外部網站存取、MCP 執行穩定性與未來擴充的可執行規範。

憲法只保留以下主幹原則：外部存取與資料處理必須具備適當的可靠性、資源控制與失敗可追蹤性；具體參數與技術方案由本文件及功能 `spec.md`、`plan.md` 定義。

## 外部請求

1. 單次外部網站請求 timeout 設定為 2 分鐘。
2. 單次外部網站請求最多 retry 3 次。
3. retry 後仍失敗時，必須回報可辨識的異常資訊，不得猜測、補造或回傳不完整成功結果。
4. retry 不得規避來源網站的頻率限制或造成不合理的重複請求。
5. retry、timeout 與異常原因必須寫入執行紀錄。

## 非同步處理

1. MCP API 採非同步處理，以避免外部網站存取阻塞 API 執行。
2. 目前不建立 Job API；非同步處理不代表必須建立 Job 資源或資料庫。
3. 若未來查詢時間、資料量或使用情境需要 Job API，必須在新的 `spec` 與 `plan` 中定義，不得由實作自行加入。

## 來源頻率與存取政策

外部網站存取必須遵守適用的來源規範，包括：

- `robots.txt` 中可識別的爬取限制。
- 網站使用條款。
- 官方 API 文件或存取政策。
- 官方公告的頻率、速率或合理使用限制。

`robots.txt` 不一定會定義頻率限制；即使存在 `Crawl-delay`，也可能不被所有網站或工具支援。因此不能只依賴 `robots.txt` 判斷允許的請求頻率。

若來源規範未說明頻率、規範互相衝突或無法確認允許的存取方式，必須停止查詢或回報異常，不得自行猜測。

各網站 `spec.md` 必須定義適用的來源規範、請求頻率與必要的等待或 backoff 行為；不得低於本文件要求。

## 未來持久化

目前不建立資料庫或 Repository 保存查詢紀錄。若未來需要保存查詢紀錄、執行狀態或結果，必須另行提出需求，評估資料庫、Repository、保存期限與資料存取政策。

## 驗證與紀錄

每次請求至少應能確認：

- timeout 與 retry 設定有生效。
- retry 次數未超過上限。
- 來源頻率與存取政策未被違反。
- 失敗時能取得異常原因。
- 執行紀錄包含必要的請求、重試與結果資訊。
